# Platform Review — July 2026

A gap analysis of this repository against the ASHG 2026 workshop abstract, audience
rationale, and organizer talking outline for *Modeling Choices in Omics: Implications for
Health Disparities in Human Genetics*.

**Scope.** This review maps each checkable claim in the workshop materials to evidence in
the repository. It is written to be shared with a co-organizer, so it states problems
plainly rather than diplomatically.

**Baseline state at time of review.** `npm run validate:data` passes (5 bundles).
`npm run test` passes (4 unit tests). The application builds and the primary participant
path works end to end. The findings below are not "the prototype is broken" — they are
"the prototype does substantially less than the workshop materials say it does."

**Repository state.** Everything here was scaffolded in a single commit (`fae723a`,
"initial draft of the ASHG 2026 workshop") and has not been revisited since.

---

## A. The interaction model is a facade

**Severity: highest.** This is the finding that most directly undermines the workshop.

The abstract's central mechanic is that participants "make analytic choices via
sliders/toggles" and "observe how results change in real time." Verified by searching all
of `apps/web/src`:

- Only the `modelId` control is ever read, through `selectedModelId()`
  (`apps/web/src/scenarioUtils.ts:12`).
- All five sliders across the five scenarios — `ancestryMix`, `heterogeneity`,
  `regionWindow`, `sampleSize`, `lambda` — are rendered by `ControlPanel.tsx` and written
  into React state, and **no code reads them.** `ScenarioCharts.tsx` never consults
  control state except via `selectedModelId`.
- Even `modelId` mostly changes only bar *opacity* (`ScenarioCharts.tsx:55`,
  `ScenarioCharts.tsx:115`). The subgroup-calibration and coefficient-path charts ignore
  the selected model entirely.

A participant who drags "Regularization strength" from 5 to 90 sees nothing change. In a
workshop whose entire thesis is *analytic choices have consequences*, a control that
demonstrably has no consequence teaches the opposite lesson. This is worse than having no
slider at all.

## B. Most of the documented data schema is unused

The following top-level bundle fields appear **only in `apps/web/src/types.ts`** and in
no component:

`ancestryGroups`, `alleleFrequencies`, `simulatedEffects`, `powerEstimates`,
`localAncestryResults`, `modelPerformance`

Everything actually rendered comes from `vizSummaries`, a `Record<string, unknown>` of
pre-shaped chart arrays. Consequences:

1. **`docs/data-schema.md` documents fields the application does not consume.** A
   contributor generating a new scenario would populate them and see nothing appear.
2. **The validator checks the wrong things.** `scripts/validate-scenarios.mjs` asserts on
   `associationResults` and `powerEstimates` while the actually load-bearing
   `vizSummaries` keys go unchecked. A typo in `effectComparisons` passes CI and fails
   silently at runtime — in the room, in front of participants.
3. **Allele frequency is never displayed anywhere.** The organizer talking outline names
   it explicitly as a teaching point ("Allele frequencies are similar, reduces power").
   The data is in every bundle and is invisible.
4. **Heterogeneity statistics are invisible.** `within-vs-meta.json` carries
   `vizSummaries.heterogeneity` (I² = 58, Cochran Q p = 0.032) and no renderer consumes
   it. That scenario's own stated learning objective is "interpret heterogeneity rather
   than treating it as a nuisance."

### Architectural note on the polling backend

Adding shared state is a real departure from the design commitments in `README.md`
("deployable as static assets behind a CDN", "no reliance on participant-side
computation") and it introduces a live dependency that can fail in front of 150 people.

The decision is to build it anyway. To contain the risk, the backend must be built as a
**separable track**: the scenario platform continues to work fully with the backend
unreachable, and polling degrades to "unavailable" rather than blocking a module. Load
testing must then cover concurrent writes to the backend, not just cached CDN reads —
the 75-150 user claim is about the weakest component, which is no longer the CDN.

**Note on the first row.** For a workshop tracked under ELSI and pitched to a methods
audience, "our simulations are empirically calibrated" is the claim most likely to be
challenged from the floor, and it is currently unsupported by any artifact in the repo.
This is the largest single credibility exposure.

**Note on polling.** Building it requires a backend, which contradicts the static-CDN
deployment plan in `deploy/aws-s3-cloudfront.md` and the "no reliance on participant-side
computation" resilience argument. An external polling tool costs nothing architecturally.

## Facilitator credential drift — 2026-09-28

A fifth deploy-only defect, found by trying to sign in: **the two facilitator gates were
deployed with different passwords.** The edge gate accepted the pair in `apps/web/.env.local`,
which the stack's `FacilitatorBasicAuth` parameter had been built from; the in-app gate
accepted the `VITE_FACILITATOR_PASSWORD` repository secret, which is what the bundle is
compiled with. The two had drifted, so the browser prompt opened for one password and the form
behind it demanded another. The run sheet was unreachable with any single pair.

Two things made it survive every check:

- **A secret's value cannot be read back.** `deploy/README.md` said the secret "must match the
  Basic auth pair above" and nothing enforced it. The stack was built from a local file on the
  assumption that it matched, which could not be verified at the time.
- **The verification tested one gate against its own source.** Curling `/facilitator` with the
  pair from `.env.local` confirmed the edge function agreed with the file it had been generated
  from, and said nothing about the app. Same shape as the e2e guard noted under Verification in
  `AGENTS.md` that passed against the code it was written to catch.

The deployed bundle is what settles it: Vite inlines the credential as a string literal, so
`curl`-ing `assets/index-*.js` and reading the value is a direct check of what the app will
accept. Both gates are now aligned on the secret's value, which the app was already shipping.

The fix that matters is in `.github/workflows/deploy.yml`: the smoke check now requests
`/facilitator` with the pair compiled into the build and fails on anything but 200, after first
confirming an anonymous request still gets 401 — without that ordering a missing edge function
would pass by admitting everything. This is the same reasoning as the signed-POST check added
earlier: assert the thing that breaks in the room, at the layer where it breaks.

## Deployed — 2026-09-16

The stack is up and the workshop has a URL on the CloudFront distribution (tag
`v1.0.0-ashg`). Five weeks before Montréal, so the Pages contingency stays a backup and is
not triggered.

**The concurrency claim is now closed rather than half closed.** 200 concurrent writes
against the deployed backend completed in 1842 ms with all 200 recorded, 50 per option —
the DynamoDB `ADD` path holds under the opening-question burst. Every previous run of this
check measured a process on a laptop.

Deploying surfaced four defects, none of which any local check, any CI run, or the Pages
backup could have caught, because each one only exists where the repository meets a real
AWS account and a real GitHub OIDC token:

1. **The runbook's SSO role name was wrong.** `deploy/README.md` documented
   `AdministratorAccess`; Identity Center provisioned `AWSAdministratorAccess`. With the
   documented value `aws sso login` succeeds and every subsequent call fails at
   `GetRoleCredentials` with a bare `ForbiddenException: No access` — which reads as a
   missing entitlement and sends you back to CloudOps for an access problem you do not have.

2. **The deploy role could not be assumed at all.** `heart-gen` has GitHub's immutable OIDC
   subjects enabled, so the `sub` claim is
   `repo:heart-gen@<orgId>/omics-modeling-choices-platform@<repoId>:environment:production`.
   The numeric ids sit immediately before the `/` and the `:`, so no `repo:owner/repo:*`
   pattern can match. The failure is `Not authorized to perform sts:AssumeRoleWithWebIdentity`,
   which names neither the claim nor the pattern; CloudTrail's `userIdentity.principalId` is
   what identifies it. The role now trusts both subject forms.

3. **`lambda:GetFunctionConfiguration` was missing from the deploy role.**
   `aws lambda wait function-updated` polls it, and `lambda:GetFunction` does not imply it.
   The Lambda code shipped and *then* the workflow failed on the wait — a deploy that had
   really happened reported as a failure.

4. **The load test could not reach a deployment.** `waitUntilReady` probed `/health`, which
   is not an `/api/*` route, so CloudFront sends it to S3 and it never parses as JSON. The
   test would have reported "Polling service did not become ready" against a healthy
   backend — and this is the command both `deploy/README.md` and the rehearsal checklist
   name as the way to substantiate the 75-150 user claim. It now probes the poll snapshot.

Defect 2 is the one worth remembering: the trust policy was *written* correctly against the
documented subject format, and GitHub changed what it sends. It cannot be caught by review,
only by a real token.

Also verified at the edge: all six bundles and all seven polls return 200; the three cache
classes match the documented policy; module 3's 1.33 MB bundle is served gzipped at 126 KB;
and the facilitator path returns 401 without credentials, 401 with wrong ones, and the app
shell with the right pair, so the base64 header comparison is correct. That last check was
weaker than it looked — it only tested the edge gate, against the same file the edge gate had
been built from. See "Facilitator credential drift — 2026-09-28".

Still open, and all of it needs a person rather than code: the production URL on conference
Wi-Fi or an equivalently constrained network, the poll projected and read from the back of a
room, the six-module manual walkthrough against the production URL, and NUIT's FY26-27
purchase order for the account.

**Pedagogical audit.** Five of six modules demonstrably argue what they claim:
pooled-vs-stratified (pooled 0.058 → 0.034 across the mix slider while stratified estimates
hold), within-vs-meta (I² 0 → 88.6, random-effects CI width 0.039 → 0.120 while fixed stays
flat), global-vs-local (global p=0.48, local-as-covariate p=0.38, interaction p=4.4e-08),
regularization (group-aware calibration 0.92 → 0.38 while shared collapses 0.85 → 0.00),
scalability (permutation scan 11,111 h / 555.6 h / 37.0 h against a 168 h bar).

**`complexity-power` was the weak one, and has been retuned.** At n=250 power ran
0.38 / 0.37 / 0.25 across minimal / balanced / high-complexity. The balanced arm — the
*default* — sat within 0.01 of minimal, so a participant who never changed the model saw no
tradeoff at all, and the module argued "extreme over-adjustment hurts" rather than
"adjustment is a tradeoff." The cause was the covariate ladder: since the cost term is
`k/n`, 15 covariates in 250 people absorb only 6% of genotype variance.

Covariate counts are now 5 / 60 / 160, stated in each control label so the `k/n` arithmetic
is visible rather than hidden behind an adjective. Power separates 0.38 / 0.31 / 0.17 at
n=250 and converges 0.95 / 0.95 / 0.93 at n=1200. The stronger result is on significance:
the three models cross alpha at ~350, ~420, and ~570, so at the default n=500 the saturated
model reports p=0.052 while the other two are significant — from an identical point
estimate. That is the module's own first learning objective ("recognize over-adjustment as
a source of false negatives") demonstrated on one screen rather than asserted.

`beta` was deliberately left at 0.24. Raising it widens the arms but pins all three at 1.00
by n=1200, which hides the convergence the slider exists to show.

One layout fix followed: the association summary table is now full-width
(`.chart-card.association-summary`). At half the grid width its p-value column sat outside
the visible area and had to be scrolled to — tolerable when the module was about interval
width, not tolerable now that significance is the point. This clipping predates this pass;
it is visible in the committed July figures.

## How to verify the work

- `npm run validate:data` — the extended validator must reject a bundle with a missing or
  misspelled `vizSummaries` key. Add a deliberately broken fixture and confirm it fails.
- `npm run test` — unit tests for the control-state resolver (keyed and flat-array
  fallback), and for `parseLocation` across `/facilitator` plus hash combinations, which
  is the regression guard for defect #1.
- `npm run test:e2e` — add a case that moves a slider and asserts a chart series value
  changes, and one that signs in as facilitator, clicks "Open module", and asserts the
  scenario page renders. Both fail against the current code.
- **Manual, and non-optional:** run `npm run dev` and walk all five modules end to end,
  moving *every* control and confirming something visibly changes. This is the check that
  would have caught the inert sliders.
- Regenerate bundles via the new generator and confirm `git diff` on `data/scenarios/` is
  empty or explainable — this is what proves the committed data actually came from the
  generator.
- Full rehearsal against `workshop/rehearsal-checklist.md` using the production URL.
